### 4.4. (Комбінування) Юридичні особи з великих міст

```sql

-- Бізнес-логіка: цільова аудиторія для B2B-пропозицій у ключових регіонах

FROM customers
```

### 1. Що таке SQL і для чого він призначений? Декларативна vs імперативна мова

**SQL (Structured Query Language)** — стандартизована мова для роботи з реляційними базами даних: визначення структури (DDL), маніпулювання даними (DML), вибірки даних (DQL) та контролю доступу (DCL).

SQL є **декларативною** мовою: ми описуємо *що* хочемо отримати, а не *як* це зробити. Наприклад, `SELECT * FROM customers WHERE city = 'Київ';` лише описує бажаний результат — СУБД сама вирішує, використати індекс чи повне сканування таблиці.

В **імперативній** мові довелося б явно писати алгоритм: відкрити таблицю → пройтись циклом по кожному рядку → перевірити умову city = 'Київ' → якщо істинно, додати рядок у результат → повернути список. SQL звільняє розробника від опису цих кроків.

### 2. Порядок виконання частин SELECT запиту

Логічний порядок виконання: **FROM → WHERE → SELECT → ORDER BY → LIMIT**, хоча в тексті запиту ми пишемо їх у порядку `SELECT → FROM → WHERE → ORDER BY → LIMIT`.

Розуміння цієї послідовності важливе, бо:
- WHERE не може використовувати псевдоніми (aliases), задані в SELECT, — адже SELECT виконується *після* WHERE.
- LIMIT застосовується вже до відсортованого набору даних, тому без ORDER BY результат буде непередбачуваним.
- Помилки в складних запитах часто виникають саме через невірне уявлення, на якому етапі "існують" ті чи інші стовпці.

### 3. Різниця між операторами = та LIKE

`=` перевіряє **точну відповідність** значення. `LIKE` перевіряє **часткову відповідність за шаблоном** із символами `%` та `_`.

```sql
-- = використовуємо, коли знаємо точне значення
SELECT * FROM orders WHERE order_status = 'delivered';

-- LIKE використовуємо для пошуку за фрагментом тексту
SELECT * FROM customers WHERE contact_name LIKE '%Олекс%';
```

`=` доцільний для точних кодів, статусів, ID. `LIKE` — для текстового пошуку, коли відома лише частина назви чи імені.

### 4. Призначення wildcards % та _ в LIKE

- `%` — замінює будь-яку кількість символів, включно з нулем.
- `_` — замінює рівно один символ.

Їх можна вільно комбінувати в одному шаблоні:

```sql
-- Ім'я, що починається на "Іван" і має ще рівно 1 символ
SELECT * FROM customers WHERE contact_name LIKE 'Іван_';

-- Телефон формату +380 і рівно 9 цифр після
SELECT * FROM customers WHERE phone LIKE '+380_________';
```

### 5. Чому WHERE company_name = NULL не працює

`NULL` означає "невідоме значення", а не "порожнє" чи "нуль". Будь-яке порівняння з `NULL` (навіть `NULL = NULL`) повертає не `TRUE`/`FALSE`, а результат **UNKNOWN**, який у `WHERE` трактується як `FALSE`. Тому такий запит завжди поверне 0 рядків.

Правильно — використовувати спеціальні оператори:

```sql
SELECT * FROM customers WHERE company_name IS NULL;      -- фізичні особи
SELECT * FROM customers WHERE company_name IS NOT NULL;  -- юридичні особи
```

### 6. Різниця між AND та OR, вплив пріоритету операторів

`AND` вимагає, щоб **усі** умови були істинними. `OR` вимагає, щоб хоча б **одна** умова була істинною.

**AND має вищий пріоритет за OR**, тому вираз `A OR B AND C` інтерпретується як `A OR (B AND C)`, а не `(A OR B) AND C`. Це може призвести до неочікуваних результатів:

```sql
-- Може дати непередбачуваний результат:
WHERE category_id = 1 OR category_id = 2 AND unit_price > 20000;
-- Реально виконується як:
WHERE category_id = 1 OR (category_id = 2 AND unit_price > 20000);
```

Тому рекомендується завжди явно розставляти дужки, навіть коли пріоритет здається очевидним.

### 7. Коли BETWEEN включає граничні значення

`BETWEEN` **завжди включає обидві границі** (еквівалентно `>=` та `<=`) і ніколи не виключає їх автоматично.

Щоб виключити границі діапазону, потрібно замінити `BETWEEN` на строгі нерівності:

```sql
-- НЕПРАВИЛЬНО (спроба виключити границі через BETWEEN):
WHERE unit_price BETWEEN 10001 AND 49999;

-- ПРАВИЛЬНО:
WHERE unit_price > 10000 AND unit_price < 50000;
```

### 8. Призначення LIMIT та OFFSET, формула пагінації

`LIMIT` обмежує кількість рядків у результаті. `OFFSET` пропускає задану кількість рядків перед початком вибірки. Разом вони реалізують пагінацію (розбиття результату на сторінки).

**Формула:** `OFFSET = (номер_сторінки - 1) × розмір_сторінки`

```sql
-- Сторінка 3, розмір сторінки 10 -> OFFSET = (3-1)*10 = 20
SELECT * FROM products ORDER BY product_name LIMIT 10 OFFSET 20;
```

### 9. Чому ORDER BY важливий разом з LIMIT

Без `ORDER BY` СУБД **не гарантує** порядок рядків — він залежить від внутрішніх факторів (план виконання, фізичне розташування на диску, паралельне сканування, робота VACUUM тощо). Тому `LIMIT` без сортування може повертати різні набори рядків при повторних запусках того самого запиту, навіть якщо дані не змінювались.

Це особливо небезпечно для пагінації: без стабільного `ORDER BY` одні й ті самі записи можуть з'явитися на кількох сторінках або взагалі не з'явитися.

### 10. Різниця між LIKE та ILIKE в PostgreSQL

`LIKE` — чутливий до регістру пошук за шаблоном. `ILIKE` — специфічна для PostgreSQL нечутлива до регістру версія.

```sql
SELECT * FROM customers WHERE contact_name LIKE 'іван%';   -- НЕ знайде "Іван"
SELECT * FROM customers WHERE contact_name ILIKE 'іван%';  -- знайде "Іван", "ІВАН", "іван"
```

`LIKE` доцільний, коли регістр даних гарантовано однорідний (наприклад, коди товарів у верхньому регістрі). `ILIKE` — коли користувач вводить пошуковий запит вручну і регістр непередбачуваний (пошук по імені, назві товару тощо).

### 11. Обробка NULL при сортуванні, NULLS FIRST/LAST

За замовчуванням PostgreSQL трактує `NULL` як значення, "більше" за будь-яке інше. Тому:
- При `ORDER BY column ASC` — рядки з `NULL` опиняються **в кінці**.
- При `ORDER BY column DESC` — рядки з `NULL` опиняються **на початку**.

Цю поведінку можна змінити явно, незалежно від напрямку сортування:

```sql
SELECT * FROM customers ORDER BY company_name NULLS LAST;   -- NULL в кінці
SELECT * FROM customers ORDER BY company_name NULLS FIRST;  -- NULL на початку
```

### 12. Бізнес-сценарій зі складною комбінацією умов у дужках

**Приклад:** потрібно знайти товари, які або є "преміальними" (сума понад 20000 грн у категоріях 1–2), або є "бюджетними" (будь-якої категорії, але дешевші за 5000 грн) — для формування списку пріоритетної обробки складом.

```sql
SELECT *
FROM products
WHERE (category_id IN (1, 2) AND unit_price > 20000)
   OR (unit_price < 5000);
```

Якщо забути дужки і написати `category_id IN (1, 2) AND unit_price > 20000 OR unit_price < 5000`, результат формально буде той самий через пріоритет AND над OR — **але** це працює лише випадково для цього конкретного випадку. Щойно логіка ускладнюється (додається третя умова чи інший OR), відсутність дужок легко призводить до того, що умова застосовується не до тієї групи полів, яку мав на увазі розробник. Дужки роблять намір явним і незалежним від запам'ятовування правил пріоритету.
